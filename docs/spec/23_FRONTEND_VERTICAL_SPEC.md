## Responsibility

This document defines the complete frontend architecture for RealmForge: stack, workspace
structure, component contract, Visual Map integration, accessibility baseline, testing
strategy, and build pipeline. Every frontend implementation decision is traceable to this
document or to ADR-0002.

Boards is the first frontend vertical. Everything built here establishes the pattern for
Knowledge, Build Watch, Live Watch, and all subsequent UI surfaces.

## The `ui/` Package Contract

**Rule:** Every component used across more than one feature must live in `src/components/ui/`.
shadcn/ui primitives are installed into this directory and immediately wrapped with our named
component. Consumers never import from shadcn/ui directly — they import from `@/components/ui/`.

**Why this rule exists:** ADR-0002 identified the risk of shadcn/ui copy-paste erosion.
If engineers import shadcn primitives directly in feature code, the component layer
becomes unowned and unmaintainable. The `ui/` package is the enforcement boundary.

Code review must reject any import of `@/components/ui/[shadcn-primitive]` from feature
code. Feature code imports only from `@/components/ui/[our-named-component]`.

### Component Contracts

Each component's contract specifies: props, events, accessibility behavior, and usage
constraints. These are not implementation details — they are the public API.

---

#### `<BoardCard>`

```typescript
interface BoardCardProps {
  boardId: string;
  title: string;
  state: BoardState;                  // 10 states from spec
  lastUpdated: Date;
  primaryAction?: {
    label: string;                    // visible text, also aria-label if icon-only
    onClick: () => void;
    disabled?: boolean;
    disabledReason?: string;          // surfaced to screen readers via aria-describedby
  };
  children?: React.ReactNode;
}
```

**Accessibility contract:**
- Root element is `<article>` with `aria-labelledby` pointing to the title heading
- `primaryAction` button has a visible label (never icon-only without text equivalent)
- `disabled` state uses `aria-disabled="true"` AND `disabled` attribute (not just visual style)
- `disabledReason` is connected via `aria-describedby`

---

#### `<BoardStateChip>`

```typescript
type BoardState =
  | 'intake' | 'mapping' | 'review' | 'approved'
  | 'execution' | 'verification' | 'release_ready'
  | 'released' | 'blocked' | 'archived';

interface BoardStateChipProps {
  state: BoardState;
  size?: 'sm' | 'md';
}
```

**Accessibility contract:**
- Renders as `<span>` with `role="status"` when used in a live region context
- Color is never the only differentiator — each state has a distinct icon + text label
- `blocked` state triggers `aria-live="polite"` announcement in the nearest live region

#### `<DataTable>`

```typescript
interface DataTableProps<TRow> {
  columns: ColumnDef<TRow>[];
  data: TRow[];
  totalCount: number;
  pagination: {
    pageIndex: number;
    pageSize: number;
    onPageChange: (page: number) => void;
  };
  isLoading?: boolean;
  emptyState?: React.ReactNode;
  caption: string;                    // Required — describes the table for screen readers
}
```

**Accessibility contract:**
- Renders as `<table>` with `<caption>` (not `aria-label` — native caption is preferred)
- Column headers use `<th scope="col">` with explicit scope
- Sortable columns: `aria-sort="ascending" | "descending" | "none"`
- Loading state: `aria-busy="true"` on the table element
- Pagination controls are a `<nav aria-label="Table pagination">` with landmark role
- Row actions have accessible names independent of their position in the table

#### `<GraphCanvas>` (React Flow wrapper)

```typescript
interface VisualNode {
  id: string;                         // VN-* node ID from the spec
  type: 'module' | 'phase' | 'decision' | 'workpath';
  data: {
    label: string;
    state?: string;
    metadata?: Record<string, unknown>;
  };
  position: { x: number; y: number };
}

interface VisualEdge {
  id: string;                         // VE-* edge ID from the spec
  source: string;
  target: string;
  label?: string;
  type?: 'dependency' | 'handoff' | 'data-flow';
}

interface GraphCanvasProps {
  nodes: VisualNode[];
  edges: VisualEdge[];
  onNodeClick?: (nodeId: string) => void;
  onEdgeClick?: (edgeId: string) => void;
  readOnly?: boolean;
}
```

**Accessibility contract:**
- The graph canvas has `role="img"` with `aria-label` describing the graph content
- A text-alternative list of nodes and edges is provided in an off-screen `<details>`
  element for screen reader users (`aria-describedby` points to it)
- Node click actions are keyboard-accessible (Tab to focus, Enter/Space to activate)
- Focus moves to the detail panel when a node is activated (not just highlighted)
- Color alone does not encode node type or state — shape + label are always present

**Performance contract:**
- Up to 500 nodes must render without frame drops on simulated mid-tier mobile
- Nodes beyond the viewport are virtualized by React Flow (do not disable virtualization)
- Pan and zoom interactions are smooth on 4x CPU throttle

#### `<RealTimeFeed>`

```typescript
interface RealTimeFeedProps {
  endpoint: string;                   // SSE endpoint URL
  renderItem: (event: unknown) => React.ReactNode;
  maxItems?: number;                  // default 100 — older items are pruned
  pauseWhenHidden?: boolean;          // default true — pause SSE when tab is backgrounded
  'aria-label': string;               // Required — describes the live region
}
```

**Accessibility contract:**
- Wraps content in `<div role="log" aria-live="polite" aria-label={props['aria-label']}>`
- New events are appended, not prepended — screen readers announce additions in order
- A "pause updates" toggle is visible and keyboard-accessible (evidence Board may have
  rapid event streams that overwhelm screen reader announcement queues)
- If the SSE connection drops, a visible + announced status message appears

## Visual Map Integration (React Flow)

The Visual Map (`MOD-VISUAL-MAP`) renders the product graph: modules as nodes (`VN-*`),
relationships as edges (`VE-*`). The Work Path Board's primary view is this graph.

### Data flow

```
GET /v1/work-paths/{id}
    └── returns: nodes[], edges[], metadata
            └── GraphCanvas
                    ├── <ReactFlow nodes={...} edges={...} />
                    │       ├── <VisualNode /> (custom node type)
                    │       └── <VisualEdge /> (custom edge type)
                    └── graph.store.ts (Zustand) — selection state, zoom level
```

### Custom node types

React Flow custom node registration:

```typescript
const nodeTypes = {
  module:   VisualModuleNode,
  phase:    VisualPhaseNode,
  decision: VisualDecisionNode,
  workpath: VisualWorkPathNode,
} satisfies NodeTypes;
```

Each custom node type is a React component. It receives `data` from the `VisualNode` type
above. It renders: an icon (aria-hidden), a visible label, and a state indicator
(color + icon — never color alone).

### Interaction: node selection

When a node is clicked or activated via keyboard:
1. Node is marked `selected` in React Flow state
2. A detail panel slides in from the right with node metadata
3. Focus moves to the detail panel's heading (`useEffect` + `ref.current.focus()`)
4. Pressing Escape closes the panel and returns focus to the node

This focus management pattern is required for keyboard and screen reader users. No exceptions.

## Board Interaction → Bounded Command Pattern

Every primary board action emits a bounded command through the governance kernel.
The UI pattern is:

```
User clicks "Approve Board"
    │
    ├── useMutation (from boards.gen.ts)
    │       └── POST /v1/commands  { action: "command.board.approve", ... }
    │
    ├── Optimistic UI: BoardStateChip transitions to "approved" immediately
    │
    ├── On success: React Query invalidates board query → refetch confirms server state
    │
    └── On error: Optimistic update rolled back, error announced via aria-live region
```

**The UI never computes board state transitions.** State machine logic lives in
`authority-domain` on the Rust side. The UI only reflects what the backend returns.
If the backend returns `blocked`, the UI shows `blocked`. No client-side state machine.

## Accessibility Baseline

**Minimum standard:** WCAG 2.1 Level AA. Non-negotiable.

**Target screen readers:**
- VoiceOver (macOS / Safari) — primary
- NVDA (Windows / Firefox) — primary  
- VoiceOver (iOS / Safari) — secondary (mobile boards views)

**Color contrast:**
- Normal text: 4.5:1 minimum (AA)
- Large text (≥ 24px regular or ≥ 18.67px bold): 3:1 minimum
- UI components and focus indicators: 3:1 against adjacent colors
- Enforced via Tailwind's color token system — custom colors require a contrast
  check before being added to `tailwind.config.ts`

**Color as sole information carrier:** Forbidden. Every state that uses color also uses:
- A text label, OR
- An icon with `aria-label`, OR
- A pattern or shape distinction

`BoardStateChip` is the canonical example: `blocked` is red + stop-circle icon + "Blocked" text.

**Focus management rules (every interactive component):**
1. Modals: trap focus when open, return focus to trigger on close
2. Dropdowns: return focus to trigger on close or selection
3. Dynamic content: when content appears in response to user action, focus moves to it
4. Toasts/notifications: do not receive focus automatically (use `aria-live="polite"`)
5. Page navigation: focus moves to `<main>` skip-link target or page heading on route change

**Skip navigation:** A skip-to-main-content link is the first focusable element on every
page. It is visually hidden until focused, then visible. This is not optional.

## API Consumption Rules

Per the pipeline contract in `docs/api/OPENAPI_PIPELINE.md`:

1. No hand-written `fetch` or `axios` calls anywhere in feature code
2. All API calls go through generated hooks from `src/api/hooks/`
3. The custom fetch wrapper (`src/api/client.ts`) is the only place base URL and auth
   headers live
4. All error states the API contract defines must be handled — loading, empty, error, data
5. Never assume an optional field is present — check nullability per the generated types
6. Paginated endpoints use `useInfiniteQuery` from the generated hooks — never manual offset tracking

## Testing Strategy

### Component tests (Testing Library)

Every `ui/` component has a component test that covers:
- Renders with required props
- All interactive states (disabled, loading, error)
- Keyboard navigation paths
- Axe accessibility scan (zero violations)

```typescript
import { render, screen } from '@testing-library/react';
import { axe } from 'jest-axe';
import { BoardCard } from '@/components/ui/board-card';

it('passes axe accessibility audit', async () => {
  const { container } = render(
    <BoardCard boardId="b-001" title="Login Intake" state="intake" lastUpdated={new Date()} />
  );
  const results = await axe(container);
  expect(results).toHaveNoViolations();
});
```

### E2E tests (Playwright)

Every Board view has an E2E test covering the golden path:

```
Intake Board:
  1. Navigate to /boards/intake
  2. Verify page heading and board list render
  3. Click "Approve Intake" on a board item
  4. Verify board state transitions to "mapping"
  5. Verify audit event appears in Evidence Board feed

  Accessibility:
  6. Run axe scan — zero violations
  7. Tab through all interactive elements — verify focus order
  8. Activate approve action via keyboard (Enter key)
```

### Accessibility E2E (axe-playwright)

A dedicated `tests/e2e/accessibility/axe-audit.spec.ts` runs Axe against every route
on every PR:

```typescript
for (const route of ALL_ROUTES) {
  test(`${route} passes axe audit`, async ({ page }) => {
    await page.goto(route);
    const results = await new AxeBuilder({ page }).analyze();
    expect(results.violations).toEqual([]);
  });
}
```

This runs in CI on every PR. A PR with accessibility violations does not merge.

## Component Implementation Order (Phase 6)

Priority is driven by Boards vertical dependency. Build in this order:

1. **`src/api/client.ts`** — the custom fetch wrapper. Nothing else can be tested without it.
2. **`<DataTable>`** — used by Evidence Board, Cost Board, Audit view. Highest reuse.
3. **`<BoardCard>` + `<BoardStateChip>`** — used by all six Board views.
4. **`<CommandStatusBadge>` + `<PacketStatusBadge>`** — inline status indicators.
5. **Session feature** — login flow, session state in Zustand.
6. **Intake Board** (`VIEW-BOARDS-INTAKE`) — first board view. Simplest data shape.
7. **`<GraphCanvas>` + `<VisualNode>` + `<VisualEdge>`** — React Flow integration.
8. **Work Path Board** (`VIEW-BOARDS-WORKPATH`) — first graph-rendering view.
9. **`<RealTimeFeed>`** — SSE wrapper.
10. **Evidence Board** (`VIEW-BOARDS-EVIDENCE`) — first real-time view.
11. **Packet Board** (`VIEW-BOARDS-PACKET`)
12. **Release Board** (`VIEW-BOARDS-RELEASE`) — rollback preview panel.
13. **Cost Board** (`VIEW-BOARDS-COST`)

Each component must pass the Component Build Checklist before handoff to Meg (QA).

## Closed Decisions (Council 2026-05-04)

All three open questions were resolved by Council session on 2026-05-04.

1. **SSE — CLOSED (ADR-0003):** `<RealTimeFeed>` uses SSE (`EventSource`). All live
   feeds are unidirectional. WebSocket is deferred until a bidirectional use case is
   justified. Dmitri to add `GET /v1/audit/stream` as an SSE endpoint.

2. **Bearer token — CLOSED (ADR-0004):** `client.ts` sends `Authorization: Bearer <session_token>`.
   The `session_token` from `POST /v1/login` is the bearer credential. `X-Session-Id`
   is retired as an auth header. Dmitri to add Bearer extraction middleware and
   redact the Authorization header in TraceLayer.

3. **Same-origin hosting — CLOSED (ADR-0005):** React SPA is served as static files
   from the Axum binary. `VITE_API_BASE_URL=""`. No CORS required. CDN migration is
   explicitly deferred to Phase 2 with a required ADR. Dmitri to add catch-all
   route + `tower-http` ServeDir for `frontend/dist/`.
